# P3-FANOUT Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let recon/scan discovery run several independent same-tool calls concurrently (bounded, deduped,
backoff-aware), starting with nuclei, instead of one target at a time.

**Architecture:** A new poll-driven module `mcp-servers/fanout.py` manages a `_Batch` of targets using only
`job_runtime.start_job()`/`poll_job()` (already non-blocking) — no new threading. Each `check_batch()` call
polls whatever's in flight, retires anything terminal, and backfills free slots from the pending queue, gated
by a per-tool cap that persists across batches via a small per-engagement state file whenever a target gets
rate-limited/WAF-blocked. `nuclei-mcp/server.py` gets two new batch-start tools plus `check_batch()`, built on
top of this.

**Tech Stack:** Python stdlib only (`time`, `uuid`, `json`, `os`) + this repo's existing `job_runtime`,
`work_registry`, `file_lock`, `engagement_paths` modules. FastMCP for the two new nuclei-mcp tools.

**Spec:** [docs/superpowers/specs/2026-11-09-p3-fanout-design.md](../specs/2026-11-09-p3-fanout-design.md)

## Global Constraints

- Discovery only — never used by exploit-agent/chain-planner or anything feeding CEM evidence.
- No new runtime dependency; stdlib + existing modules only.
- No change to any existing tool's schema/contract (`scan_target`, `scan_with_templates`, `check_scan` on
  nuclei-mcp keep working exactly as today) — fan-out is additive (`mcp-servers/CLAUDE.md` compatibility rule).
- Every underlying job still goes through `job_runtime.start_job()` unchanged, so `budget_guard.enforce()`
  fires exactly once per real tool call, same as any non-batched scan.
- Backoff is persistent across batches (per `(tool_name)`, see Task 3 — not reset just because a new
  `start_batch()` call begins).
- Per-tool caps and the cooldown window are env-var configurable, following the `HUNTMCP_<NAME>` convention
  (`budget_guard.py:46`).

## Review Focus

- **A batch where every target is already in flight (work_registry says so for all of them):** `start_batch`
  must still return a valid `batch_id` with everything marked `skipped_in_flight` and overall `status: "done"`
  immediately — not hang waiting for slots that will never open, and not crash on an empty `in_flight` dict.
- **`check_batch()` called with an unknown/already-fully-collected `batch_id`:** must return a clear error
  dict, not a `KeyError` — mirrors `poll_job()`'s own "no job with job_id=..." shape.
- **Two blocks against the same tool in quick succession:** the second block must compound (halve again from
  the already-reduced cap, not reset back to the full default) — a cap that silently resets on a second,
  worse block would defeat the entire anti-false-negative point of persisting it.
- **Cooldown expiring exactly between two `check_batch()` calls:** the cap must ramp back to the tool's full
  default on the next call once `blocked_until` has passed, not stay permanently reduced.
- **An empty `targets` list passed to `start_batch()`:** must return an immediately-`"done"` batch with no
  targets, not loop forever or divide by zero computing a cap.

and returns the same snapshot `check_batch()` would. `_fill_slots()` loops while
`len(batch.in_flight) < DEFAULT_CAPS.get(batch.tool_name, DEFAULT_CAP_FALLBACK)` and `batch.pending` is
non-empty: pop the next target, call `batch.prepare(target)`; if it has `"error"`, record
`{"kind": "prepare_error", "error": ...}` into `results` and continue the loop (does not consume a slot);
otherwise call `job_runtime.start_job(batch.tool_name, **prepared, jobs=jobs)` and store the returned
`job_id` in `in_flight[target]`. `check_batch()` looks up the batch (returning
`{"error": f"no batch with batch_id={batch_id!r}"}` if missing — mirrors `poll_job()`'s unknown-id shape),
polls every `in_flight` entry via `job_runtime.poll_job()`, moves any whose result's `"status"` key is not
`"running"` into `results` as `{"kind": "job_result", **result}` and drops it from `in_flight`, calls
`_fill_slots()` again, and finally pops the whole batch out of `batches` once `pending` and `in_flight` are
both empty (same "pop on terminal" convention as `poll_job()`), returning `status: "done"`.

### Task 3: Persistent per-tool backoff on a block signal

**Files:**
- Modify: `mcp-servers/fanout.py`
- Test: `tests/test_fanout.py`

**Interfaces:**
- Consumes: `file_lock.locked(path: str)` (context manager); `engagement_paths.resolve(filename: str, override_env: str) -> str`.
- Produces: `_effective_cap(tool_name: str, path: str | None = None) -> int`; `_record_block(tool_name: str, path: str | None = None) -> None`. `_fill_slots()`'s slot ceiling becomes `_effective_cap(batch.tool_name)` instead of the raw `DEFAULT_CAPS` lookup. `check_batch()` calls `_record_block(batch.tool_name)` whenever a terminal job's result carries a truthy `"block"`.

Backoff state lives in one JSON file, same shape/locking convention as `work-registry.json`:
`{"<tool_name>": {"cap": int, "blocked_until": <unix timestamp>}}`. Default path via
`engagement_paths.resolve("fanout-backoff.json", override_env="HUNTMCP_FANOUT_BACKOFF_PATH")`. Keyed by
`tool_name` only (not per-target): a real WAF/rate-limiter typically throttles by source IP/request volume,
not by which specific hostname was hit, so a block anywhere for a tool should make the *whole tool's* next
batches cautious, not just the one target that happened to trip it. This is a deliberate scope decision —
the design doc left exact granularity open ("`host_or_target_prefix`"); treating the whole tool as the unit
is simpler and matches how rate-limiting actually tends to work, at the cost of being unable to distinguish
"this one subdomain is extra sensitive" from "my source IP is now throttled everywhere." Fine print for a
future refinement, not required here.
